## 这不是一份网页，而是两端产品

| 端 | 定位 | 状态 |
|---|---|---|
| **微信小程序端** | **主端** —— 承载留存 | 开发雏形（`/miniprogram`） |
| Web 端 | 承接分享、拉新、演示 | 已上线（`index.html`） |

**为什么主端选小程序，而不是网页？**

技能互换的履约发生在「约定的时间、双方到场」，
核心动作是**提醒、确认、打卡** —— 这些都要靠**主动触达**才能完成。

网页做不到这件事：用户关掉标签页，你就再也叫不回他。
而小程序有微信服务通知，能在互试课开始前把用户拉回来。

> **留存的本质是「能不能再次触达」。这正是小程序端存在的理由。**

---

## 这是什么

一个「技能互换平台」的产品设计原型。用户发布**「我能教的」**和**「我想学的」**，
平台负责把他们匹配起来并推动互换完成。

**要解决的问题**：很多人想学新技能，但报班贵、自学难坚持；同时自己擅长的技能
又缺少分享和变现渠道。技能互换看起来是双赢解法，但真正做起来卡点很多。

---

## 核心洞察：双重巧合

技能互换要求 **A 能教的 = B 想学的**，**且 B 能教的 = A 想学的** ——
两个条件必须同时成立，这是**双边匹配**，不是单边。

按 100 个技能标签、每人能教/想学各 3 个估算：

| 指标 | 数值 |
|---|---|
| 单向命中概率 | ≈ 8.7% |
| **双向同时命中** | **≈ 0.8%** |

也就是说，**一千次配对里只有约 8 次能真正换起来**。用户来两次没结果就走了，
产品根本转不动。

> **所以第一性问题不是「界面怎么设计」，而是「怎么打破双边锁死」。**
> 页面上所有机制都围绕这一件事展开。

## 设计了什么

### 五项机制

| 机制 | 作用 |
|---|---|
| **① 技能币** | 把「双边易货」降级为「多边交易」—— 我教你赚币，用币去学别人，不再要求双方刚好互补。**这是破解双重巧合的根本手段** |
| **② 三层匹配漏斗** | L1 精准互匹（体验最优）→ L2 技能币匹配（保证有结果）→ L3 技能环三人循环（冷启动兜底） |
| **③ 互试一节课** | 双方各教 30 分钟、免费，双向评价后再决定是否继续 —— 启动成本从「报名一门课」降到「聊半小时」 |
| **④ 双向信用分** | 完成互换加分、鸽人扣分；评价**双向对称**，不只学员评老师，老师也评学员「好不好教」 |
| **⑤ 技能地图** | 把「人列表」换成「技能节点 + 供需状态」，平台可立刻识别哪项技能供不应求 |

### 六阶段履约链路

```
① 破冰 → ② 互试课 ★ → ③ 定计划 → ④ 履约跟踪 → ⑤ 完成结算 → ⑥ 身份转化 ★
```

每一阶段都标注了**流失点与对策**。其中：

- **② 互试课** 是关键取舍点（决定「是否继续」）
- **⑥ 身份转化** 是**增长命门** —— 学会的技能自动加入「我能教」清单，
  把学员变成老师。**如果用户学完就走，平台永远缺老师、永远要靠补贴拉供给。**

### 增长飞轮

```
更多学习者 → 更多互换需求 → 学成者转为老师 → 供给池扩大
    ↑                                              ↓
    └────────── 匹配成功率上升 ←──────────────────┘
```

**前提**：匹配率低于阈值时飞轮根本不会转。**这也是技能币是「启动器」
而不是增长手段的原因 —— 它决定了飞轮能不能被推动第一圈。**

## 小程序端（主端）

### 如何运行

1. 下载 [微信开发者工具](https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html)
2. 「导入项目」→ 目录选 **`MT/miniprogram`**
3. AppID 选「测试号」（`project.config.json` 中已配置为 `touristappid`）
4. 编译即可运行，无需后端（雏形用本地缓存模拟数据）

### 页面与 Web 端板块的对应关系

| 小程序页面 | Web 端板块 |
|---|---|
| 首页 | 技能名片 + 匹配入口 |
| 匹配 | 04 · 可交互演示（三层策略） |
| 我的互换 | 六阶段履约链路 |
| 我的 | 增长飞轮（身份转化） |

### 留存设计：三处刻意的取舍

**① 首页第一屏是「今日待办」，不是「开始匹配」**

拉新靠匹配，留存靠待办。用户第二次打开小程序，往往不是想匹配新人，
而是**因为有一节没上的课**。

**② 订阅消息只在「点击」时请求，不在启动时弹窗**

`wx.requestSubscribeMessage` 只能由用户点击行为触发（微信硬性限制），
这恰好符合产品原则：**在用户最需要提醒的那一刻要授权，通过率最高**。
所以授权入口出现在「开启履约提醒」按钮和「提醒对方」动作里 ——
而不是一进小程序就弹窗要权限。

**③ 第 6 阶段「身份转化」写成了真实的状态流转**

打卡推进到第 6 阶段时，学会的技能会**自动从「我想学」移入「我能教」**，
并奖励 2 枚技能币。这是增长飞轮在代码层面的落地 ——
**不是画在 PPT 上的箭头，而是真的会改变用户数据的逻辑。**

### ⚠️ 订阅消息需配置模板 ID

`miniprogram/app.js` 中的模板 ID 目前是占位值：

```js
templates: {
  trialRemind: 'REPLACE_WITH_YOUR_TMPL_ID',    // 互试课提醒
  confirmRemind: 'REPLACE_WITH_YOUR_TMPL_ID'   // 确认与履约提醒
}
```

**必须替换**：微信公众平台 → 功能 → 订阅消息 → 申请模板 → 填入模板 ID。
未替换时点击订阅会**明确弹窗提示**（不会静默失败），其余功能不受影响。

消息下发还需服务端调用 `subscribeMessage.send`（可用云开发云函数实现），
雏形中已保留完整的客户端调用逻辑。

## 可交互的部分

打开原型页后，找到「**04 · 可交互演示**」板块：

1. 左侧是「我的技能名片」（能教：吉他弹唱 / 摄影构图；想学：Python 入门 / 视频剪辑）
2. 点击 **「开始匹配」**
3. 页面会**依次跑三层匹配**：L1 精准互匹 → L2 技能币匹配 → L3 技能环撮合
4. 注意看 L2 出现时，**右上角的技能币会从 3 扣到 1** —— 用一次真实操作演示
   「技能币如何把双边巧合拆成单边匹配」
